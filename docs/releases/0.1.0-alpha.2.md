# PayoutJP 0.1.0-alpha.2

Core/Bank/CLI are published under the npm `alpha` tag. A clean Registry consumer verified
all three package versions/checksums, public APIs, and the sample correction workflow.

This alpha adds a local Bank CSV workflow: create a fictional sample, audit recipients using an
explicit mapping, locate failing rows/fields, correct the source data, and rerun the same command.

## Install and try

Node.js 24 is required:

```sh
npm install --global @payoutjp/cli@0.1.0-alpha.2
payoutjp init --template bank-csv --directory ./payoutjp-demo
cd payoutjp-demo
payoutjp doctor
payoutjp audit recipients.csv --profile bank-generic-jp@0.1.0 --mapping columns.json --locale ja
```

The second fictional recipient intentionally fails with exit code 1. Manually change its fictional
account number from `12X4567` to `0123456` and rerun to get PASS. Values are never corrected automatically.

## Changes

- Bank-only JSON/CSV batch audit with one Profile, explicit column/account-type mapping, stdin,
  source locations, per-row schema findings, and complete canonical report v1 output.
- Japanese human diagnostics, `init`, `doctor`, and local Profile/Registry inspection.
- Prepared Bank validators with owned immutable snapshots and reusable Registry indexes.
- Bounded input, capped human output, atomic report writes, protected source/config/artifact paths,
  and metadata-only Bank/branch observations for incorrectly mapped sensitive values.
- Node 24 Ubuntu/macOS/Windows verification, fixed LF checkouts, synthetic benchmarks, and clean
  packed-consumer checks.

## Migration from alpha.1

Existing single JSON `validate` and report v1 remain supported. Bundled Profile/Registry versions
and contents are unchanged. Invalid destination IDs now produce input errors rather than internal
errors. Bank/branch observed displays are metadata-only; consumers should use canonical finding IDs/fields.

New audit IDs are generated from row order by default. `--id-policy input` requires unique,
non-sensitive metadata IDs of at most 128 characters. Replacing an audit report requires
`--overwrite-report`. Existing single `validate` report replacement remains supported, with atomic
writes and input/config/artifact protection. Text shows at most 100 findings; JSON retains all results.

## Validation and limits

All three OS jobs passed 365 tests in [main CI](https://github.com/inthecradle/payoutjp/actions/runs/37107502679).
Linux production dependency audit, packed Core/Bank/CLI consumers, and synthetic performance checks passed.
The earlier Linux measurement on Node 24.21.0 was 287/301 ms median for 10,000 normal/10%-invalid
rows and 287 MiB peak RSS. These are synthetic results; independent usability evaluation remains pending.

Input limits: 50 MiB, 100,000 rows/findings, 64 KiB CSV record, 8 KiB field. Malformed files,
conflicting Profiles, unsupported rails, explicit-ID violations, and resource limits abort the command.
Row schema issues use `INPUT-SCHEMA-001` while remaining rows continue.

No production Bank Registry is bundled. This release does not execute transfers or prove account
existence, identity, wallet ownership, or payment success. JPYC CLI, YAML destination input,
mixed-rail/Profile batches, Scanner, and the dedicated Action remain deferred.
